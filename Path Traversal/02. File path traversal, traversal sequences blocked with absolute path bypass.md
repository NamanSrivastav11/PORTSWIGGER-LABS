This lab blocks classic traversal strings `../`, but the backend still accepts absolute filesystem paths.
So instead of trying to climb directories, we can try to point directly at the target file.

---------------------------------------------------

## Steps

We can start with the standard interception step to identify where image paths are supplied:

<img width="522" height="126" alt="image" src="https://github.com/user-attachments/assets/8f1ce598-6b57-4bc3-a62f-cdc4f831aae3" />

Since the page references the product images as file names, indicating a possible path traversal vulnerability.

Tried the familiar traversal payload:

```http
GET /image?filename=../../../etc/passwd HTTP/2
```

<img width="1562" height="939" alt="image" src="https://github.com/user-attachments/assets/81207625-329c-498f-bb2c-a74f52c030c6" />

This request failed to expose `passwd` content, which suggests traversal patterns are being filtered or normalized.

Next, I tried checking for whether the application validates path **type** or only path **pattern**. So we can try by giving a direct absolute path:

```http
GET /image?filename=/etc/passwd HTTP/2
```

<img width="1920" height="1120" alt="image" src="https://github.com/user-attachments/assets/a2358ba4-7760-460d-aea8-bb686808a003" />

This time the response included `passwd` enteries; so the validation is incomplete. It blocks `../`, but still allows arbitrary absolute paths from the fielsystem root.

Hence, the lab is marked as completed.
