# File path traversal, traversal sequences stripped non-recursively

<img width="915" height="286" alt="image" src="https://github.com/user-attachments/assets/53ac8b15-f012-4761-8d14-2a7d7bff1e82" />

---------------------------------------------

- Reference: https://portswigger.net/web-security/file-path-traversal

---------------------------------------------

In this lab, the application tries to sanitize path traversal by stripping `../` from user input.
The observed flaw was that stripping was done only once (non-recursive), so a crafted playload can still be processed into traversal after partial filtering.

---------------------------------------------------

## Steps

From exploring the product page, we can observe that the image files are loaded through the following request

<img width="1687" height="606" alt="image" src="https://github.com/user-attachments/assets/195b62c9-787f-4539-87dc-0315b8790508" />

This indicates that the user-controlled input (`filename`) is used to build a filesystem path on the server.

So, we can try with a normal path traversal test: 

```text
../../../etc/passwd
```

Send a request to Burp Repeater and modify tthe request with the above payload

<img width="1687" height="984" alt="image" src="https://github.com/user-attachments/assets/a540e5a4-3a41-4c99-b714-b6438f8f5c3d" />

We can see that the our modified request may be blocked or sanitized, which suggests some filtering is active.

-------------------

So, if the application strips `../` exactly one time, then this payload:

```text
....//....//....//etc/passwd
```

is transformed like this:

```text
....//....//....//etc/passwd
    -> (single-pass removal of ../ patterns)
../../../etc/passwd
```

After sanitization, valid traversal sequences still remain and are interpreted by the filesystem when resolving the final path.

That is the core bug: **single-pass sanitization instead of cannonical path validation**.

------------

So now, we will send the following request from Burp Repeater:

```html
GET /image?filename=....//....//....//etc/passwd HTTP/2
```

<img width="1920" height="1122" alt="image" src="https://github.com/user-attachments/assets/d2871360-740d-480e-b856-70b06cfde765" />

As we can see that the path is resolved by the backend, and the response returns the contents of `/etc/passwd`.


Once `/etc/passwd` is dosclosed, the lab is marked as solved.
