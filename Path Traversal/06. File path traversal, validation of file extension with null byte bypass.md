## Lab Description

This lab exposes a file retrieval endpoint that expects image filenames and enforces a policy requiring the requested path to end with a specific extension. The validation logic is intended to prevent direct access to non-image resources such as system files.

---------------------------------------------

- Reference: https://portswigger.net/web-security/file-path-traversal
  
---------------------------------------------

## Analysis

In this lab, the application attempts to enforce safe file access by requiring that requested path ends with an allowed extension, typically `.png`.

The request flow usually begins with a parameter such as `filename=33.png`, which is appended to a base path but in this lab, direct payloads like `../../../etc/passwd` fail because they do not satisfy the extension requirement.

On attempting a payload like `../../../etc/passwd.png` might pass the extension check but fails to return sensitive data because no file with that extension exists.

---------------

URL-encoded null byte injection is represented as `%00`. When decoded, `%00` becomes the null character (`\x00).

> Histrically, many native components and some backend integrations treat `%00` as a string terminator when converting request data for file APIs.
> 
> At validation time, the application treats the parameter as an ordinary string and checks for an allowed suffix such as `.png`.
> At execution time, a lower-level routine receives a null-terminated string and truncates everything after `\x00`.
>
> This means that an input like `../../../etc/passwd%00.png` can appear compliant during extension validation and yet get resolved as `../../../etc/passwd` during file access.


## Exploit Construction

Now we know that we need a payload that must satisfy two conditions simultaneously:

- It must include traversal to reach the sensitive target file, and
- It must still appear to end with the required image extension when the application checks it.

We will place the null byte in-between those two parts so that hte suffix is visible to validation logic but invisible to the final open operation.

**PAYLOAD:**

```text
../../../etc/passwd%00.png
```

Input: `../../../etc/passwd%00.png`  

After URL decode: `../../../etc/passwd\x00.png`  

After extension validation: accepted, because application-level string ends with `.png`  

During file open: interpreted as `../../../etc/passwd` due to null-termination  

Final resolved path: `/etc/passwd`
