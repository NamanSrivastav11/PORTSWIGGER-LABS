## Lab Description & Analysis

The application enforces a brute-force protection mechanism that locks an account after a fixed number of consecutive failed login attempts.
If repeated failures occur for a valid account, the system transitions that account into a locked state and returns a response indicating the lockout condition.

The flaw lies in how this lockout behavior is applied. The lock is triggered only for valid usernames, since non-existent users do not have an associated account state to transition into. As a result, repeated login attempts with an invalid username will never produce a lock-related response, whereas valid usernames will eventually trigger an explicit **account locked** condition.

-----------

## Understanding the Lockout Behavior

To verify the lockout behavior, I intercepted the login request in Burp Suite and sent it to Intruder.

I configured a simple attack using an invalid username and generated multiple identical login requests using a **Null Payload**.

### Intruder Configuration

- **Attack Type:** Sniper
- **Username:** `carlos`
- **Password:** `password`
- **Payload:** Null Payload (50 iterations)

No account lockout message appeared, even after fifty consecutive requests.

This confirms that the application does **not** lock requests based solely on repeated login attempts from a client. Instead, the lockout appears to be tied to existing user accounts.


## Enumerating a valid Username

This time I wanted to send several login attempts for **every candidate username** 

Configure the attack as follows:

- **Payload Position:** Username parameter
- **Password:** A fixed invalid value (e.g., `password` or `test`)
- **Payload List:** Provided username wordlist

For each username, let's allow the application to process multiple failed login attempts and observe how it responds.
