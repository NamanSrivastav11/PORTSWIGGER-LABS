## Lab Description and Observations

- Feedback function (`/feedback`) contains a blind OS command injection vulnerability.
- The application executes a shell command containing user-supplied details from the feedback form.
- Command output is **not** returned in the HTTP response.
- There is a writable folder on the server:
  ```text
  /var/www/images/
  ```

Product images are serverd from this folder via a `/image` endpoint.

Goal: execute `whoami`, redirect its output into `/var/www/images/`. then retrieve the results via the image-loading URL.

------------------------------------------------

The lab uses a blog application with a **Submit feedback** page that has a form with:
- Name

## Confirming blind command injection

We first confirm there is a command injection in one of the feedback parameters, using the same approach as in the time-delay lab.

The request is sent to Burp Repeater, and each parameter is tested with a time-delay payload.

<img width="1561" height="416" alt="image" src="https://github.com/user-attachments/assets/e1f6324b-c5e1-4bdc-a766-825da50112ac" />

Starting from the `email` parameter.

PAYLOAD: `email=test@test.com||ping+-c+10+127.0.0.1||`


> `||` is a shell operator: "execute right-hand command if left-hand command fails"
> 
> If the original command part involving `email` fails or returns non-zero, `ping -c 10 127.0.0.1` will run.
> 
> `+` in the payload is interpreted as a space in URL-encoded form, so the actual shell command becomes `ping -c 10 127.0.0.1`.

When sent via Burp Repeater, the response takes about 10 seconds, confirming that `email` is part of a shell command and is injectable.

Findings:
- The feedback handler executes a shell command using the `email` input.
- We can inject arbritrary shell syntax into `email`.

## Crafting the output-redirection payload

Linux shells allow redirecting _stdout_ to a file with `>`.

PAYLOAD: `/var/www/images/whoami.txt`

This writes the output of `whoami` into a file that the web app can serve.
I'll splice this into the existing shell command built by the application, and ideally ignore any trailing noise that might cause errors.

```|| whoami > /var/www/images/whoami.txt ||``` or ```& whoami > /var/www/images/whoami.txt ||```

```||``` ensures the command runs if the original segment fails.
```>``` redirects the command's output to the specified file.

A trailing `||` or `#` can be used to neutralize anything that comes after, depending on how the shell command is built.
